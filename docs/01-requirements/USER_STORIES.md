# 单笔宣传物料订单交付管控系统 · 用户旅程与原子故事分解

> **文档类型**：敏捷需求分解
> **角色范围**：客户经理 / 业务负责人 / 设计制作人员
> **故事数量**：22 条
> **版本**：MVP v0.1

## 01 产品定位与 MVP 范围

本系统通过**标准化流程链路、角色权责隔离与设计版本全留痕**，实现单笔宣传物料订单从需求登记到客户确认交付的全流程闭环管控，解决传统即时通讯沟通模式下的需求传递失真、版本混淆不清、进度分散难追踪、权责边界模糊等行业痛点。

MVP 阶段聚焦最小可用的"需求—版本—确认"闭环：一个订单从客户经理登记需求开始，经业务负责人审阅派发、设计制作人员执行与版本上传、内部评审放行、客户评审反馈、迭代直至客户确认交付，全程在系统内留痕、可追溯。

### 1.1 本期纳入（MVP 闭环）

| # | 模块 | 说明 |
|---|---|---|
| 1 | 订单需求登记 | 标准化表单（物料类型 / 规格 / 场景 / 截止日期）+ 参考素材上传 |
| 2 | 需求基线确认 | 提交前形成可追溯的需求版本 |
| 3 | 任务分派与流转 | 业务负责人审阅、退回、派发、设截止 |
| 4 | 设计版本管理 | 上传自动编号、历史留痕、版本对比 |
| 5 | 进度跟踪 | 我的订单 / 看板状态总览 |
| 6 | 内部评审与放行 | 版本审核、放行至客户评审 |
| 7 | 客户评审与反馈 | 版本级反馈条目化记录 |
| 8 | 客户确认与交付闭环 | 确认留痕、终稿标识、归档 |

### 1.2 暂不纳入（后续迭代）

| # | 模块 | 说明 |
|---|---|---|
| 1 | 合同与财务 | 报价、合同、开票、收款 |
| 2 | 在线设计 | 系统内置设计 / 协作画布工具 |
| 3 | 印刷生产 | 对接印刷厂、生产排程、工单 |
| 4 | 物流配送 | 发货、物流跟踪、签收 |
| 5 | 外部消息通知 | 微信 / 短信 / 邮件等外部渠道推送 |

> **说明**：外部消息通知指对外部渠道（微信 / 短信 / 邮件）的推送；MVP 内**站内提醒**（待办、状态变更）属于闭环内必要能力，予以保留。

## 02 三角色端到端用户旅程地图

先以一条**跨角色主流程**呈现单笔订单的端到端流转链路与各环节归属角色，再分别展开客户经理、业务负责人、设计制作人员三段详细旅程。

### 2.1 跨角色主流程链路

| 环节 | 名称 | 主责角色 |
|---|---|---|
| 01 | 需求登记 | 客户经理 |
| 02 | 需求基线确认 | 客户经理 |
| 03 | 审阅与派发 | 业务负责人 |
| 04 | 设计执行 | 设计制作人员 |
| 05 | 版本上传 · 内部评审 | 设计 → 业务 |
| 06 | 客户评审与反馈 | 客户经理 |
| 07 | 迭代与终稿 | 设计 → 业务 |
| 08 | 客户确认 · 交付归档 | 客户经理 / 业务 |

> 环节 05 / 07 涉及跨角色交接。

## 03 核心原子化用户故事

以下 22 条故事严格遵循 **INVEST** 原则与"作为一名…我希望能够…以便…"三段式，按角色分组。每条故事独立可估、可测、可交付，共同构成 MVP 极简闭环。

### INVEST 合规说明

所有故事均满足：

| 字母 | 原则 | 含义 |
|---|---|---|
| **I** | Independent（独立） | 可独立交付 |
| **N** | Negotiable（可协商） | 细节可协商 |
| **V** | Valuable（有价值） | 对端到端闭环有明确价值 |
| **E** | Estimable（可估算） | 规模可估算 |
| **S** | Small（小巧） | 单次迭代内可完成 |
| **T** | Testable（可测试） | 验收标准可测 |

下表"验收要点"列即为每条故事的可测边界。

---

### 3.1 客户经理故事（AM-01 ~ AM-08）

> 需求登记 → 客户评审 → 确认交付

| 编号 | 用户故事 | 验收要点 |
|---|---|---|
| **AM-01** | **作为一名** 客户经理，**我希望能够** 通过标准化表单登记一笔宣传物料订单（物料类型、规格尺寸、使用场景、交付截止日期、参考素材），**以便** 需求一次成型、避免即时通讯口头传递造成的**需求传递失真**。 | 订单创建后含上述必填字段；关键字段缺失时无法提交。 |
| **AM-02** | **作为一名** 客户经理，**我希望能够** 在提交订单前上传客户提供的参考文件与素材，**以便** 设计人员拥有明确的创作依据。 | 订单可附加多文件；附件与订单关联且可在详情页查看下载。 |
| **AM-03** | **作为一名** 客户经理，**我希望能够** 将已确认需求的订单一键提交给业务负责人审阅派发，**以便** 订单进入标准化流转链路而非依赖私人沟通。 | 提交后状态变为"待派发"并出现在业务负责人待办中。 |
| **AM-04** | **作为一名** 客户经理，**我希望能够** 随时查看我所负责订单的当前状态与所处环节，**以便** 不再通过即时通讯反复询问进度，解决**进度分散难追踪**。 | 我的订单列表显示每单当前状态与所处阶段，无需询问他人。 |
| **AM-05** | **作为一名** 客户经理，**我希望能够** 将某个设计版本分享给客户进行在线评审，**以便** 客户反馈与具体设计版本一一对应、避免**版本混淆**。 | 可对指定版本发起客户评审；客户反馈绑定该版本编号。 |
| **AM-06** | **作为一名** 客户经理，**我希望能够** 在系统中记录客户对某版本的具体修改意见并关联至该版本，**以便** 设计人员准确接收反馈、**权责清晰**。 | 反馈以条目形式记录并显示在对应版本下，设计人员可见。 |
| **AM-07** | **作为一名** 客户经理，**我希望能够** 在客户确认最终版本时记录确认时间与确认版本号，**以便** 交付有据可查、避免事后争议。 | 确认操作记录确认人、时间与版本号，记录不可篡改。 |
| **AM-08** | **作为一名** 客户经理，**我希望能够** 在交付完成后将订单标记为已交付，**以便** 订单闭环并归档全流程记录。 | 标记后订单进入"已交付"终态；全流程时间线可回溯。 |

| **BO-08** | **作为一名** 业务负责人，**我希望能够** 在客户确认后确认订单最终交付并闭环归档，**以便** 订单全流程记录完整可追溯。 | 确认交付后订单终态为"已交付"；全流程时间线可导出查看。 |

## 04 MVP 闭环验证与痛点覆盖

### 4.1 闭环链路自洽性验证

将 22 条故事按主流程首尾相连，可验证 MVP 已形成**从需求登记到客户确认交付的完整闭环**：

1. **需求入口（AM-01 / AM-02）**：客户经理以标准化表单 + 素材登记订单，需求基线一次成型。
2. **流转提交（AM-03）**：订单提交进入业务负责人审阅队列，脱离私人沟通。
3. **审阅派发（BO-01 / BO-02 / BO-03）**：校验完整性，可退回补充；完整则派发至设计人员并设截止，责任到人。
4. **执行上传（DS-01 ~ DS-04）**：设计人员基于需求基线执行，上传自动编号版本并提交内部评审。
5. **评审放行（BO-05 / BO-06）**：业务负责人版本对比评审，放行决定留痕，版本可控进入客户评审。
6. **客户评审反馈（AM-05 / AM-06 / DS-05）**：客户反馈条目化绑定版本，设计人员准确接收迭代。
7. **迭代终稿（DS-06）**：放行后标记终稿，交付版本正确。
8. **确认交付闭环（AM-07 / AM-08 / BO-08）**：客户确认留痕、订单标记已交付、全流程归档可追溯。

> 进度跟踪（AM-04 / BO-04）与异常处理（BO-07）为贯穿闭环的横向能力，不阻断主链但保障可控性。

---

### 4.2 四大痛点覆盖矩阵

| 行业痛点 | 消解机制 | 对应故事 |
|---|---|---|
| **需求传递失真** | 标准化表单 + 需求基线 + 附件归集，需求一次成型 | AM-01、AM-02、BO-01、BO-02、DS-01 |
| **版本混淆不清** | 自动版本编号 + 历史留痕 + 版本对比 + 终稿标识 | DS-02、DS-03、BO-05、AM-05、DS-06 |
| **进度分散难追踪** | 我的订单列表 + 看板状态总览，状态实时可见 | AM-04、BO-04、DS-04 |
